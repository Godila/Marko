## 0. Главное (TL;DR)

1. **«Получение ключа», НКМТ и СУЗ — это три разных API с разными базами, но одна экосистема** с общей УКЭП-схемой входа: `GET /auth/key` → подписать `data` → `POST /auth/simpleSignIn...` → токен (10 часов).
2. **Вывод из оборота к СУЗ отношения не имеет** — он делается в True API ГИС МТ (документ LK_RECEIPT, признак DISTANCE) и уже полностью разобран в предыдущем ресерче (`wb-specs/research-log.md`). СУЗ отвечает за **эмиссию КМ** (заказ кодов, отчёты о нанесении/агрегации/выбытии). В этом документе СУЗ разобран именно как контур эмиссии.
3. **Для лёгпрома отчёт о нанесении (utilisation) НЕ отправляется участником — формируется автоматически** при выдаче КМ (метод `/api/v3/utilisation` для ТГ «Лёгкая промышленность» недоступен). Контур эмиссии для нас: `order → order/status → codes → close`.
4. НКМТ пайплайн карточки: `generate-gtins (029)` → `feed` (≤500 товаров/фид, 25 МБ) → `feed-status` → модерация → `feed-product-document` (XML) → `feed-product-sign-pkcs` (откреплённая УКЭП) → статус **published** + `good_mark_flag` → карточка готова к эмиссии КМ.
5. **Основной путь авторизации везде — единый токен True API (UUID) в Bearer**. Статический `apikey` НК формально ещё документирован (API НК v5.66 от 31.08.2026, раздел 10 True API, база знаний 28.07.2026), но по сообщению участника (письмо ЦРПТ о принудительном переходе на единый токен UUID до 01.09.2026 + практика) **уже не принимается** — не полагаться на него, заложить только Bearer.
6. Все найденные дедлайны форматов токенов: UUID-без-пары — до сентября 2026 (истекает сейчас), JWT — до конца 2026. Целиться в **единый токен (UUID)** через полный цикл `/auth/key` → подпись → `simpleSignIn` (параметр `unitedToken: true`).

## 2. Получение ключа (авторизация)

### 2.1. True API — единая аутентификация (наш основной токен)

Схема (True API, разделы 1.5.1–1.5.2):

1. `GET /auth/key` → `{ "uuid": "...", "data": "GNUFBAZBMPIUUMLXNMIOGSHTGFXZMT" }` — случайная строка на подпись.
2. Подписать `data` **присоединённой УКЭП** (base64, одной строкой без `\r\n`) на закрытом сервере (КриптоПРО) — это уже реализовано у пользователя.
3. `POST /auth/simpleSignIn` с телом:
   ```json
   { "uuid": "...", "data": "<base64 подпись>", "inn": "090201471350", "unitedToken": true }
   ```
   - `inn` — обязателен, если у физлица-подписанта есть действующая МЧД и токен берётся на организацию (наш случай: подпись директора на ИП; при МЧД от разных организаций — обязателен);
   - `unitedToken: true` — получить **единый токен в формате UUID** (см. ниже про форматы);
   - `details` — реквизиты аттестата соответствия (не наш случай).
4. Ответ: JWT → `{"token": "eyJ..."}`; UUID → `{"token": "...", "uuidToken": "...", "expireDate": "..."}`.
5. **TTL токена — 10 часов.** Далее цикл повторяется (в платформе — фоновый job через signer, ~2–3 раза в день).

Форматы токенов и дедлайны (примечания в доке True API):
- «Получение токена в формате UUID **без предварительного запроса пары** доступно до сентября 2026» — старый ленивый способ умирает прямо сейчас; всегда делаем полный цикл через `/auth/key`.
- «Поддержка токена в формате **JWT** сохранена до конца 2026» — целься в UUID (единый токен).

Типы приватности методов True API (раздел 1.6): приватный / покупатель / оператор / ФОИВ / администратор / публичный (с токеном) / без токена. Для нас важное: приватные методы — только в рамках своей товарной группы (lp подключена к ЛК).

Ошибки авторизации, которые надо обрабатывать в платформе: 400 (нет uuid/data, inn не 10/12 цифр, uuid не найден в хранилище, data не подписан УКЭП или не те данные), 403 (подписант не добавлен как пользователь организации — проверять ротацию сотрудников/МЧД).

### 2.2. СУЗ — динамический clientToken

СУЗ 3.0 авторизуется заголовком `clientToken` (не Authorization Bearer!). Токен получается **тем же True API**, но другим методом:

- `GET <true-api>/auth/key` → пара uuid/data (как обычно);
- `POST <true-api>/auth/simpleSignIn/{omsConnection}` телом `{"uuid","data","inn"?}` — подпись **присоединённая или откреплённая**;
- ответ: `{"token": "2f2222c2-..."}` — **UUID-формат, TTL 10 часов**.

`omsConnection` — идентификатор соединения (внешнего подключения/устройства). Два способа получить:

1. **Через UI СУЗ** (рекомендуемый старт): ЛК ГИС МТ → «Управление заказами» (СУЗ) → раздел «Устройства» → столбец «Идентификатор соединения». Новое устройство: «+ Создать устройство» (имя, тип **«АСУ ТП»**, режим отправки отчётов). Нужна роль «Администратор».
2. **Через API** (для зарегистрированных интеграционных решений): `POST <suz>/api/v2/integration/connection?omsId={omsId}` с заголовками `X-Signature` (подпись УКЭП) и `X-RegistrationKey`; тело `{address, name}` → `{omsConnection}`. Стенды: демо `https://suz-integrator.sandbox.crptech.ru`, прод `https://suzgrid.crpt.ru:16443`. **Демо-ключ регистрации: `4344d884-7f21-456c-981e-cd68e92391e8`** (для песочницы). Прод-ключ выдаётся Оператором после регистрации ИР и тестирования.

Критичные правила:
- **Один токен на omsConnection**: повторный simpleSignIn/{omsConnection} гасит предыдущий токен. Один signer — один флоу обновления, без конкуренции.
- **Переход необратим**: после первого успешного обращения к API СУЗ с динамическим токеном статичные токены перестают работать (нас не касается — сразу строим на динамических).
- `omsId` (идентификатор СУЗ, из UI СУЗ) — отдельная сущность, передаётся в query каждого метода СУЗ.

В СУЗ PDF есть и легаси-пути: `POST /api/v1/auth` + `/api/v1/token/{omsConnection}` — это **ИС МДЛП** (только лекарства, не наш случай). Наш путь — 9.3.2 через True API.

### 2.3. НКМТ — Bearer-токен (основной путь); apikey — не полагаться

Методы НК документируют два варианта (двойная спецификация: раздел 2.2 API НК и раздел 10 True API «Методы Национального каталога»):
- `Authorization: Bearer <true-api-token>` — токен ГИС МТ (10 ч, через signer). **Основной путь**: единый токен и так нужен для True API/СУЗ, авторизация НК через него не требует ничего дополнительного. Одновременное указание apikey и Bearer → 400 «Недопустимо использование apikey вместе с <token>».
- `?apikey=XXX` — статический ключ из ЛК НацКаталога («Профиль» → «Данные участника» → «API KEY», роль «Администратор»). **Считать устаревшим и не использовать**: по сообщению участника (сентябрь 2026) ключ уже не принимается, хотя публичная документация (API НК v5.66 от 31.08.2026, раздел 10 True API, статья базы знаний от 28.07.2026) его ещё описывает, а в анонсах API НК (v1.0–v4.0, 05.05–03.06.2026) и релиз-нотах ЧЗ августа 2026 отключение не анонсировано. Расхождение «доки пишут / жизнь отрубила» — типично для ЦРПТ; проверять живым вызовом при первом smoke-тесте (песочница `api.nk.sandbox.crptech.ru` на запрос без авторизации отвечает пустым 401).

Контекст писем ЦРПТ (2026): единый токен UUID для True API обязателен с 01.09.2026 (старая логика «UUID без пары» отключается), JWT — до конца 2026; перевод всех API экосистемы (True API, СУЗ, НК) на единую аутентификацию — «до осени 2026». Интеграционные api-key для внешних систем НК выдавались заявкой на `support@national-catalog.ru` — этот канал тоже исчерпывает себя.

Итого signer-задачи платформы по типам подписи:

| Задача | Данные | Тип подписи | Куда уходит |
|---|---|---|---|
| auth-true-api | data из /auth/key | присоединённая, base64 | simpleSignIn |
| auth-suz | data из /auth/key | присоединённая/откреплённая | simpleSignIn/{omsConnection} |
| suz-order / suz-report | путь+query (GET) или тело (POST) | **откреплённая CMS (X-Signature)** | методы СУЗ |
| nk-card-sign | XML карточки (feed-product-document) | **откреплённая CAdES pkcs7** | feed-product-sign-pkcs |
| mt-doc | product_document | откреплённая УКЭП | /lk/documents/create |

Протокол sign_gateway из брейншторма (lease-поллинг, задача = base64 payload + тип подписи) покрывает всё без переделок.

## 3. НКМТ (API Каталога маркированных товаров), v5.66

### 3.1. Общие правила

- Базы: прод `апи.национальный-каталог.рф`, тест `api.nk.sandbox.crptech.ru`. Пути `/v3/*` и немного `/v4/*` (в инструкции на docs.crpt.ru те же методы показаны с префиксом `/nk/...` — на стендах работают `/v3/...` из самого API-дока; при первом живом прогоне сверить оба варианта).
- Ответы: `format=json|xml`. Обёртка `{"apiversion":3, "result": {...}}`.
- **Лимиты**: по организации — общий (все методы) и частный (на метод) за «серию»; при исчерпании новая серия через **5 минут** от первого запроса серии. Счётчики в заголовках ответа: `API-Usage-Limit: 1/500`, `API-Method-Usage-Limit: 1/10`; при 429 — `Retry-After` (секунды). Конкретные значения лимитов организациям назначаются персонально (в примере фигурирует 500).
- **ETag-кэш** для `product`, `short-product`, `categories`, `brands`: `If-None-Match` → 304 не расходует лимит.
- Коды ответов: 200/304/400/401/403/404/413 (перевес)/429/500/501/503.
- Разрешённые Unicode-блоки для контента карточек (кириллица U+0400–04FF, латиница, спецсимволы — таблица в разделе 2.3); прочие символы **молча обрезаются** — валидатор xlsx-импорта должен проверять это заранее.

### 3.2. Статусная модель карточки

`good_detailed_status` (из `feed-product` / `short-product`):
- `draft` — черновик;
- `moderation` — на модерации;
- `errors` — требует изменений (отклонена модерацией);
- `notsigned` — модерация пройдена, ожидает подписания;
- `published` — опубликована;
- `archived` — в архиве.

Плюс флаги: `good_signed` (подписана), **`good_mark_flag` — атрибуты 1-го слоя заполнены и эмиссия КМ доступна** (это и есть «Готов к эмиссии»).

Атрибутные слои (из инструкции docs.crpt.ru): 1-й слой (базовые: ТН ВЭД, наименование, бренд...) **не редактируется после создания черновика**; 2-й — только до модерации; 3-й — после публикации.

### 3.3. Методы (все с `?apikey=` или Bearer)

**Чтение карточек (3.1):**
| Метод | HTTP | Назначение |
|---|---|---|
| `/v3/feed-product` | POST? (в доке — получение полной информации о своей карточке; фильтры по gtin/good_id) | Все атрибуты своей карточки независимо от статуса (кроме «Требует обработки») |
| `/v3/product` | GET | Информация о любой карточке (ETag; до N товаров) |
| `/v3/short-product` | GET | Краткая информация (статусы, good_mark_flag; ETag) |
| `/v3/product-list` (v4: `/v4/product-list`) | GET | Список собственных карточек кратко |
| `/v3/etagslist` | GET | Изменения по карточкам (инкрементальная выгрузка) |
| `/v3/mark-check` | POST | ≤100 кодов: `{gtins:[], tnveds:[]}` → принадлежность к маркируемым ТГ. Идеален для валидатора xlsx-импорта |

**Создание/обновление (3.2):**
| Метод | HTTP | Назначение |
|---|---|---|
| `/v3/generate-gtins` | GET `?quantity=N` или `?exist=1` | Черновики кодов товаров (тех. диапазон 029 — без членства GS1). Отдаёт `monthly-limit {limit, usage}` + `drafts[].gtin`. Не для SIM (004) |
| `/v3/feed` | POST | Создать/обновить карточки пакетом (фид). **≤500 товаров, ≤25 МБ, ≤1000 GTIN в наборе**; иначе 413. `moderation:1` — сразу на модерацию, иначе черновик |
| `/v3/feed-status` | GET `?feed_id&verbose` | Статус фида: Received/Moderated/Signed/Rejected/Processing (если Processing > суток — автоперевод в Rejected, повторить подачу) |
| `/v3/image` | — | Изменить размер фото |
| `/v3/feed-moderation` | GET `?good_id` или `?gtin&inn` | Принудительно отправить черновик на модерацию |

Формат фида: массив `entry`. Новый товар: `good_name` + `gtin` (или `is_tech_gtin:1` → авто-GTIN 029; или `is_sim` → 004). Обновление: `good_id`. Поля: `tnved` (4 или 10 знаков; 10 знаков автоматически раскладывается в атрибуты 3959+13933), `brand` (ID из справочника brands), `categories:[cat_id]` (если ТН ВЭД неоднозначен), `identified_by[]` (уровни упаковки trade-unit / inner-pack / box с multiplier), `good_attrs[]` (`attr_id`, `attr_value`, мультизначения — отдельными записями; РД — составное `номер:::дата`), `set_gtins[]` для наборов (кроме лёгпрома — набор лёгпрома задаётся иначе), `is_kit` для комплектов.

**Атрибуты и справочники (3.3):**
- `/v3/categories` — дерево категорий (можно от ТН ВЭД или ТГ);
- `/v3/attributes?tnved=|cat_id=&attr_type=a|b|m|r|o` — атрибутивная модель: все/заблокированные/обязательные/рекомендуемые/опциональные. Для лёгпрома тянуть `attr_type=m` (обязательные) + `r` (рекомендуемые) по нашим ТН ВЭД;
- `/v3/dictionary/isocountry` — страны;
- `/v3/brands` — товарные знаки (нужен ID бренда YCPB);
- `/v3/rd/suggest`, `/v4/rd-info`, `/v4/rd-info-by-gtin` — разрешительные документы (декларации/сертификаты; для одежды 2-го слоя — декларация о соответствии ТР ТС 017; составное значение `номер:::дата` в атрибуте 23557).

**Подписание карточки (3.4) — финальный аккорд публикации:**
1. `POST /v3/feed-product-document` `{goodIds:[], gtins:[], publicationAgreement:bool}` (≤10 позиций) → `xmls[] {goodId, xml}` (XML на подпись).
2. `POST /v3/feed-product-sign-pkcs` — тело: массив `[{goodId, base64Xml, signature}]`, signature = **откреплённая подпись CAdES pkcs7** этого XML в base64 → `signed[]` (карточка → **published**). Метод `/v3/feed-product-sign` (прикреплённая) — **устарел**.

**Субаккаунты (3.5)** — схема «владелец GTIN разрешает другому аккаунту эмиссию на свои коды»: `/v3/linked-accounts` (список), `/v3/linked-gtins` (что доступно), `/v3/linked-accounts-documents` (XML управления доступами), `/v3/linked-accounts-sign` (подписать разрешение УКЭП). **Ровно этот механизм нужен, если эмиссию КМ заказывает фулфилмент на наши GTIN, а не мы сами.**

### 3.4. Пайплайн карточки для платформы (НКМТ-слой)

```
xlsx-импорт → валидация (mark-check ТН ВЭД + атрибуты из /v3/attributes + unicode-фильтр)
  → generate-gtins (пакет тех. GTIN 029; следить за monthly-limit)
  → feed (moderation:0 — черновики; пачками ≤500)
  → feed-status (поллинг; Processing>24ч → Reseated → повторная подача)
  → пользователь правит errors-карточки → feed-moderation или повторный feed
  → feed-product-document (батчами ≤10) → signer (pkcs7 detached) → feed-product-sign-pkcs
  → published + good_mark_flag → экспорт «фактуры товаров» (GTIN-реестр) для фулфилмента/СУЗ
```

Примечание: подпись нужна на каждый батч ≤10 карточек; для массового импорта signer-очередь обязательна (это уже в архитектуре: задачи doc_sign).

## 4. СУЗ 3.0 (эмиссия КМ)

### 4.1. Общие правила

- Структура URL: `<стенд>/api/v3/...`. Заголовки: `clientToken` (обязателен), `Content-type/Accept: application/json`, `X-Signature` (обязателен для всех ТГ, кроме лекарств).
- **X-Signature** = откреплённая CMS-подпись (ГОСТ 34.10-2012 и др.) в base64: для **GET** подписывается путь+query (`/order?omsId=..`), для **POST** — тело. Прикреплённая подпись не поддерживается → **HTTP 413**.
- Rate limit: **≤100 rps на пару (IP, omsId)**; выше — временная блокировка источника.
- Лимиты заказа: ≤10 позиций (GTIN) в заказе; ≤2 000 000 КМ на GTIN (одна позиция) / ≤150 000 на GTIN при нескольких; ≤100 активных заказов (READY+буфер ACTIVE/PENDING) и ≤100 в очереди (CREATED/PENDING/APPROVED).
- Лимиты отчётов: ≤30 000 КМ в отчёте о нанесении, выбытии, агрегации.
- JSON строго по RFC 8259 (КМ содержат `\u001d` — групповой разделитель GS1).
- Печать DataMatrix: к строке КМ добавляется ASCII232 (признак символики FNC1) — задача фулфилмента/принтера.

### 4.2. Методы (ключевые для нас)

| Метод | HTTP | URL | Смысл |

| Проверка доступности | GET | `/api/v3/ping?omsId=` | health-check |

| Статус буфера | GET | `/api/v3/order/status?omsId&orderId&gtin` | `bufferStatus`: PENDING/ACTIVE/REJECTED...; `availableCodes`, `totalPassed`, `rejectionReason` |
| Список заказов | GET | `/api/v3/order/list?omsId=` | восстановление после потери данных |

| Повторно КМ | GET | `/api/v3/order/codes/retry` | повторная выдача |
| Атрибуты товара | GET | `/api/v3/order/product?omsId&orderId` | данные позиции заказа |

### 4.3. Заказ КМ для лёгпрома — рабочий пример из доки

```http
POST /api/v3/order?omsId=CDF12109-10D3-11E6-8B6F-0050569977A1
clientToken: 1cecc8fb-fb47-4c8a-af3d-d34c1ead8c4f
Content-Type: application/json
X-Signature: {откреплённая подпись тела}

{
  "productGroup": "lp",
  "products": [{
    "gtin": "01334567894339",
    "quantity": 2,
    "serialNumberType": "SELF_MADE",     // или генерация оператором
    "serialNumbers": ["QIQ8BQCXmSJJ", "GLTP9kqZn5QR"],  // 12 симв. при SELF_MADE (13 при операторе)
    "templateId": 10,                     // шаблон этикета лёгпрома
    "cisType": "UNIT"                     // UNIT | BUNDLE (комплект) | SET (набор) | GROUP?
  }],
  "serviceProviderId": "c5fe527a-...",   // если печать через сервис-провайдера
  "attributes": {
    "contactPerson": "Иванов П.А.",
    "releaseMethodType": "IMPORT",        // способ выпуска: PRODUCTION/IMPORT/REMAINS/REMARK...
    "createMethodType": "CM",             // устарел, валидация снята
    "productionOrderId": "08528091-..."   // свободный идентификатор (1-256)
  }
}
```

Ответ: `orderId` + `expectedCompleteTimestamp`. Далее поллинг `order/status` до `bufferStatus=ACTIVE` → `codes` пачками → `order/close`.

`OrderProduct.attributes.producer` (ИНН владельца карточки) — обязателен при `releaseMethodType` = REMARK/REMAINS и заказе на чужой/оригинальный GTIN (связка с субаккаунтами НК!).

Лёгпром-константы:
- код ТГ в СУЗ: **`lp`**; серийный номер: **13 символов** (SELF_MADE — 12);
- структура КМ (раздел 8.2 PDF): `01`+GTIN(14) + `21`+серийник(13) — код идентификации; `91`(4) + `92`(44) — код проверки. **Короткий КМ из WB excise-report (01+GTIN+21+serial = 31 симв.) — это ровно код идентификации без криптохвоста**, что подтверждает прежний вывод: для LK_RECEIPT достаточно короткого кода, полный лежит в WB orders/meta;
- набор (SET) и комплект (BUNDLE) для лёгпрома — свои cisType/templateId (таблица 8.х);
- маркировка остатков (REMAINS) — периодический режим, открывается на определённые ТН ВЭД (сейчас не актуален).

### 4.4. Отчёт о нанесении — для нас автоматически

Примечание 2 к методу utilisation: для ТГ **«Лёгкая промышленность», «Обувные товары», «Духи», «Шины», «Фотокамеры»** отчёт о нанесении **формируется автоматически** (событие квитирования `GET_CODES_GENERATED_REPORT` — «Отправка автоматически-сгенерированного отчёта о нанесении КМ»). Участник эти группы в utilisation не отправляет (метод для них недоступен). КМ после выдачи сразу считаются нанесёнными (EMITTED → APPLIED).

Следствие: цепочка СУЗ для лёгпрома — `order → order/status (ACTIVE) → codes → close`. Ввод в оборот — уже документ True API (LP_INTRODUCE_GOODS / LP_INTRODUCE_GOODS_CIS etc., разобрано ранее).

### 4.5. Выбытие/отбраковка и агрегация (справочно)

- `/api/v3/dropout` — отчёт о выбытии/отбраковке КМ **до ввода в оборот** (брак на производстве/складе фулфилмента). Отличать от вывода из оборота (True API);
- `/api/v3/aggregation` — отчёт об агрегации: `sntins` — КМ **без кода проверки** (только 01+21), `unitSerialNumber` — код агрегата (SSCC/КИ транспортной упаковки). ≤30 000 КМ на отчёт. Для FBS-потока не обязательно, пригодится фулфилменту для сборных коробов.

## 5. Вывод из оборота — где живёт на самом деле

Пользовательская формулировка «СУЗ (вывод из оборота)» смешивает два контура — зафиксирую разделение:

- **СУЗ** — только эмиссия/нанесение/агрегация/брак до оборота;
- **Вывод из оборота после продажи на WB FBS** — True API ГИС МТ: `POST /lk/documents/create?pg=lp` с типом **LK_RECEIPT** (`action=DISTANCE`, products[].cis + product_cost), коды INTRODUCED→RETIRED; **возврат после выкупа** — **LP_RETURN** (`return_type=REMOTE_SALE_RETURN`, paid=true + первичный RECEIPT), RETIRED→INTRODUCED. Детально (форматы, регламент 3 рабочих дня, фильтр FBS, связка с excise-report) — в `../wb-specs/research-log.md` и памяти; здесь не дублируется.

## 6. Выводы для архитектуры платформы

1. **Модуль `connector_mt` расширяется с одного до трёх подконтуров** (или выделяется `connector_nk`, `connector_suz`): true-api (документы оборота), nk (карточки), suz (эмиссия). Все — за общим sign_gateway.
2. **Токен-менеджер**: один UKEP-signer обеспечивает 2 вида auth (True API Bearer — он же авторизация НК; СУЗ clientToken — отдельный omsConnection!), TTL обоих 10 ч, refresh ~2–3 р/день, один активный токен на omsConnection (никаких параллельных логинов). НК ходит под тем же Bearer, что и True API — отдельного секрета не заводить (apikey не используется).
3. **Типы подписи в signer**: присоединённая (auth) и откреплённая CMS/CAdES (X-Signature СУЗ, pkcs7 карточек НК, документы True API) — подтвердить у существующего скрипта КриптоПРО способность делать detached CAdES-BES по ГОСТ (скрипт уже делает auth и откреплённую для документов — вероятно, всё есть).
4. **НКМТ-слой** (фаза 3 платформы) полностью обеспечен API: валидация (mark-check, attributes), массовое создание (feed ≤500), статусы, подписание батчами ≤10, справочники. xlsx-валидатор должен заранее фильтровать запрещённый Unicode (иначе молчаливая обрезка) и проверять monthly-limit генерации GTIN (по умолчанию в примере лимит 100/мес).
5. **Эмиссия КМ**: по вводным её делает фулфилмент (у них СУЗ/принтеры). Тогда наш контур СУЗ = read-only мониторинг их заказов на наши GTIN (через субаккаунты НК + omsConnection) — и module suz можно отложить. Если эмиссию берём на себя — все методы выше готовы, включая авто-нанесение. **Открытый вопрос для пользователя.**
6. **Тест-контур**: полный — True API sandbox + НК sandbox + СУЗ sandbox (`suz.sandbox.crptech.ru`, интеграционный демо-ключ `4344d884-...`). Прежде чем писать код, прогнать живой smoke: auth → nk mark-check → suz ping.

## 7. Открытые вопросы

1. Префикс путей НК на стендах: `/v3/...` (сам API-док) vs `/nk/...` (инструкция docs.crpt.ru) — проверить живым вызовом оба.
2. Кто заказывает КМ (мы или фулфилмент) — определяет, нужен ли модуль СУЗ в фазе 1–2 и механизм субаккаунтов НК (`linked-accounts-sign`).
3. Конкретные значения НК-лимитов для нашего аккаунта (персональные) и monthly-limit generate-gtins — узнать из ЛК/первого вызова.
4. Атрибутный состав карточки лёгпрома (attr_id 1-го/2-го слоя, ID категории одежды 2-го слоя, ID бренда YCPB) — вытащить живыми вызовами `categories` + `attributes` на тест-контуре (отдельный шаг перед реализацией xlsx-импорта; есть отдельная страница доков «Атрибутивные модели карточек товаров»).
5. ГОСТ TLS-стенды СУЗ (api.suzgrid...) — пром-пилот со 2 кв. 2027; держать в уме, пока использовать обычные.
6. `templateId=10` (пример для lp) — сверить с актуальным справочником шаблонов при первом заказе.
7. **apikey НК**: публичные доки (v5.66 от 31.08.2026, раздел 10 True API, база знаний 28.07.2026) всё ещё описывают ключ, но по сообщению участника он уже не принимается. При первом smoke-тесте проверить оба варианта на песочнице и на проде; в коде заложить только Bearer, apikey — флаг-опция для обратной совместимости. Уточнить у ТП ЦРПТ официальную дату/статус отключения.
