# Дискавери: возврат товара в оборот (WB FBS, лёгпром)

2026-09-04. Источники: дампы True API (wb-specs/trueapi-page-all.txt, v.679+), API СУЗ 3.0
(crpt-specs/API_SUZ_3.0.txt), спеки WB (12-reports.yaml goods-return), прод-фикстуры
excise-report (op=2), официальный портал ЧЗ markirovka.ru (статьи лёгпрома), ПП 1956,
прод-круг КМ 04.09 (LK_RECEIPT+LP_RETURN CHECKED_OK).

## 1. Нормативная рамка

| Что | Документ | Суть |
|---|---|---|
| Правила маркировки лёгпрома | **ПП РФ от 31.12.2019 № 1956** (акт. ред.) | Весь процесс вывода/возврата |
| Срок вывода при ДП | п. 76 ПП 1956 | Сведения о выводе при продаже по образцам/дистанционно: **не позднее 3 рабочих дней со дня отгрузки со склада хранения** и **не позднее даты фактической доставки потребителю** (оба ограничения одновременно) |
| Кто подаёт вывод при FBS | п. 76 ПП 1956 + п. 6.1 ст. 1.2 54-ФЗ | **Собственник товара** (продавец). Маркетплейс и курьер/СД не участники оборота. Чек WB при FBS бьётся без КМ (с ИНН поставщика) — двойного выбытия не будет; если позже придёт чек от ОФД, повторное выбытие не фиксируется |
| МОД при выводе | **ПП РФ от 29.12.2025 № 2192** (с 01.03.2026) + v-нота True API | При action=DISTANCE/BY_SAMPLES/RETAIL в LK_RECEIPT для ЛП обязательны `kpp` (у ИП null) и `fias_id` (ФИАС GUID места деятельности). Прод подтвердил: без fias_id — отказ «МОД не найдены» |
| Возврат покупателя | ЗоЗПП ст. 26.1 | Дистанционно купленный товар надлежащего качества: отказ в течение **7 дней** после передачи (3 месяца, если не выдана письменная памятка); ненадлежащего — в течение гарантии |
| Запрет продажи без маркировки | ПП РФ от 21.11.2023 № 1944 | (Справочно; наш товар всегда маркирован) |
| Ответственность маркетплейса | ПП РФ от 29.07.2022 № 1351 (с 01.03.2023) | FBO: маркетплейс — участник оборота и сам ведёт маркировку; FBS — НЕ участник, всё на продавце |

Срок подачи **LP_RETURN** (возврат в оборот) нормативно НЕ установлен (в отличие от вывода,
п. 76) — ни в ПП 1956, ни в статьях ЧЗ он не назван. Кассовый путь (ККТ+ОФД, мгновенно) к FBS
не применим — чек возврата бьёт WB как агент. Рабочее правило: подавать по факту физического
возврата товара продавцу и проверки КМ (goods-return `completedDt`).

## 2. Статусная модель КМ (ГИС МТ)

`INTRODUCED (в обороте)` → LK_RECEIPT (DISTANCE) → `RETIRED (выбыл)`
→ LP_RETURN (REMOTE_SALE_RETURN) → `INTRODUCED` → можно продавать снова тем же КМ. Цикл
повторяемый (перепродажа возвращённого). При перемаркировке старый КМ → `WRITTEN_OFF
(списан)` — окончательно.

## 3. Сценарии и регламентный процесс

### А. Невыкуп (покупатель не забрал в ПВЗ)
- WB: заказ `canceled_by_client`, продажи нет, excise op=1 НЕ появляется.
- ЧЗ: наш пайплайн выводит **по факту выкупа** → вывода не было → **ничего подавать не
  нужно**, КМ остаётся INTRODUCED. Товар вернётся продавцу через механизм возвратов WB.
- Альтернативные схемы (вывод при отгрузке, «до дня доставки» по п. 76) тогда требуют
  LP_RETURN и при невыкупе — мы их НЕ используем; наш триггер по выкупу п.76 формально
  соблюдает (день выкупа = день передачи).

### Б. Возврат покупателя после выкупа, КМ цел (основной кейс)
1. Выкуп: op=1 → LK_RECEIPT (DISTANCE, fias_id) CHECKED_OK → КМ RETIRED.
2. Покупатель оформил возврат (7 дней по ЗоЗПП; WB даёт больше) → сдаёт в ПВЗ.
3. WB: деньги возвращаются покупателю, с продавца удержание; товар едет на ПВЗ выдачи
   возврата продавцу; goods-return: `orderDt → readyToReturnDt → status → completedDt`,
   `expiredDt` — срок хранения.
4. Продавец забирает: по QR из ЛК WB; **хранение 7 дней (первые 3 бесплатно, дальше
   10 ₽/день за единицу)**, на 8-й день возвращают на склад WB.
5. Проверка КМ: читается → **LP_RETURN**: `return_type=REMOTE_SALE_RETURN`, `paid=true`
   (обязательно при этой причине), первичка обязательна при paid=true: `RECEIPT` +
   number/date (наш LK_RECEIPT — прод-тест CHECKED_OK 04.09; допустимые типы для
   REMOTE_SALE_RETURN: RECEIPT/SALES_RECEIPT/OTHER+custom_name). КИ должен быть RETIRED.
   → CHECKED_OK → КМ INTRODUCED.
6. Перепродажа: тот же КМ, новое сборочное задание, PUT meta/sgtin → цикл заново.

### В. Возврат с повреждённым/срезанным КМ (частый кейс одежды)
Порядок (ЧЗ «Перемаркировка», причина «Возврат в случае дистанционной продажи»):
1. **СУЗ-заказ** с `releaseMethodType=REMARK` — для ЛП доступен; на оригинальный GTIN
   (карточка наша — без `producer`; серийники в запросе НЕ указывать, первый символ
   серийника генерится как идентификатор государства «вне производства»); для ЛП
   нанесение (utilisation) автоматическое → новый КМ сразу APPLIED. Тип REAPPLY для ЛП
   НЕ доступен.
2. **LK_REMARK**: `participant_inn`, `remarking_cause=REMOTE_SALE_RETURN`
   (предыдущий КИ должен быть RETIRED именно по дистанционной продаже), `last_uin` =
   старый КМ, `new_uin` = новый (APPLIED, тип эмиссии REMARK), первичка как в LP_RETURN
   (RECEIPT/SALES_RECEIPT/OTHER), `remarking_date` не старше 5 лет и не будущая.
   Данные цвет/размер/страна берутся из last_uin.
3. Итог: старый КМ WRITTEN_OFF, новый INTRODUCED; физически наклеить новый КМ → продавать.
Восстановить прежний повреждённый КМ нельзя; отказать покупателю в возврате из-за
отсутствия КМ нельзя (ЗоЗПП).

### Г. Брак / гарантийный (claims)
WB returns-api `/api/v1/claims` — заявки покупателей (окно 14 дней), ручное решение по
каждой; товар возвращается тем же механизмом; ЧЗ-сторона = сценарий Б или В.

## 4. Сигналы WB API (триггеры возврата)

| Сигнал | Метод | Что даёт | Лимиты (базовый токен) |
|---|---|---|---|
| **excise-report op=2** (главный) | seller-analytics `POST /api/v1/analytics/excise-report` | `excise_short` (КМ 31 симв.), srid, **фискальные данные чека возврата WB** (fiscal_doc_number/drive/dt), price | 2/24ч, интервал 12ч |
| goods-return (физическое движение) | seller-analytics `GET /api/v1/analytics/goods-return` | orderId, srid (ID заказа на возврат), status, `completedDt` (выдача продавцу), `expiredDt`, reason, returnType, ПВЗ выдачи | 2/ч, интервал 30 мин; окно ≤31 день |
| sales R-строки | statistics `GET /api/v1/supplier/sales` | Финансовый возврат (saleID R…); srid возврата ≠ srid продажи — связка только по КМ | 1/2ч |
| claims | returns-api `/api/v1/claims` | Гарантийные заявки | — |

Прод-фикстуры: 40 op=2 строк за 3 мес (все FBW, WB сам делал вывод/возврат) — формат
подтверждён живьём; для FBS строк ещё не было (KnownUnknown №1: появится ли op=2 у
FBS-возврата, где вывод подавали мы; WB знает КМ из meta/sgtin — ожидаем, что да).

## 5. Известные неизвестные (закрываются первым живым FBS-возвратом)

1. Появляется ли op=2 в excise-report для FBS-возврата (у нас вывод свой, WB — только
   чек возврата). Ожидание: да, по закреплённому sgtin.
2. Хронология: op=2 появляется в момент приёмки ПВЗ или выдачи продавцу (completedDt)?
3. Совпадает ли srid в op=2/goods-return/sales-R (для дедупа событий).
4. Скорость статусов goods-return для FBS (готовность к выдаче).

## 6. Гэпы текущей реализации платформы (факты, не рецепты)

- `return_batch` (emitter) строит LP_RETURN с первичкой из НАШЕГО LK_RECEIPT — прод-тестом
  CHECKED_OK; фискальные данные чека возврата WB из op=2 при этом не используются (допустимо).
- Перемаркировка (СУЗ REMARK-заказ + LK_REMARK) не автоматизирована — ручной путь через ЛК ЧЗ.
- Мониторинг goods-return (дедлайн забора 7 дней / expiredDt) не ведётся — операционный риск
  пропустить забор и потерять товар/деньги.
- claims-api не подключён.
- Пайплайн корректно не требует ничего при невыкупе (вывод по факту выкупа).

## 8. Дополнение 05.09: разъяснение WB от 04.09.2026 — повторная продажа зависит от формата КИЗ в сборочном задании

Источник: памятка с форума, разъяснение поддержки WB 04.09.2026 (не офиц. дока; WB обещал
обновить инструкции/новости при изменениях — перепроверять).

**Подтверждает нашу схему:** УПД ДОП при FBS НЕ нужен; первая продажа — продавец выводит сам
(наш LK_RECEIPT по excise op=1); возврат — продавец возвращает (LP_RETURN); КИЗ не передан /
автовозврат → товар в ПВЗ продавцу.

**Новое — кто выводит при ПОВТОРНОЙ продаже (после возврата):**
- **ПОЛНЫЙ КИЗ** (GS-разделители + криптохвост) в сборочном задании → WB сам включает его в чек
  повторной продажи и выводит **по ККТ на продавца**. Продавцу повторно не выводить, УПД не нужен.
- **КОРОТКИЙ КИЗ** → WB не может включить в чек; повторную реализацию отслеживает и выводит
  САМ продавец (ровно то, что делает наш конвейер: op=1 → LK_RECEIPT).
- Вывод: передавать в сборочное задание только ПОЛНЫЙ КИЗ (WB и так требует полный в meta/sgtin
  с 03.06.2026) → мы в «полной» ветке.

**Гэпы платформы (код не менять до решения юзера):**
1. **Двойной вывод**: WB-ККТ-вывод повторной продажи, вероятно, появится в excise как op=1 с
   новым FBS-srid → наш автомат RETURNED+sale→PENDING_WITHDRAW создаст LK_RECEIPT по уже-RETIRED
   коду → отказ ЧЗ. Нужен гвард: отказ «код не в обороте/уже выбыл» → помечать WITHDRAWN
   (вывел WB по ККТ), не аномалия; опционально пре-чек статуса КМ через API ЧЗ до создания документа.
2. **Несовпадение причин**: WB-ККТ-вывод = причина RETAIL → возврат ТАКОЙ продажи требует
   return_type=RETAIL_RETURN (первичка — чек возврата, его фискальные данные есть в excise op=2),
   а return_batch жёстко шлёт REMOTE_SALE_RETURN (batch.py:114 — соответствует только
   DISTANCE/BY_SAMPLES). Нужен выбор причины по источнику последнего вывода (наш LK_RECEIPT vs
   WB-ККТ).
3. Стейт-машина в остальном справляется: WITHDRAWN+return→PENDING_RETURN уже есть.
