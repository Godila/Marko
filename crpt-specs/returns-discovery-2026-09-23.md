# Дискавери 23.09.2026: возвраты покупателей и невыкупы — живая картина

Обновление к returns-discovery-2026-09-04.md. Источники: прод-БД (wb.returns 750 строк,
журнал, cis_sync 23.09), живые WB orders/meta + ЧЗ cises_info (64 КМ), код платформы.

## 1. Главные живые факты

1. **goods-return = 100% невыкупы**. 750 строк за 07–22.09, из них 748 — returnType
   «Возврат товара, который приехал по МП, продавцу», 2 — «неверное вложение».
   **Ни одна строка не связана с заказом, имеющим событие продажи** (ret_with_sale_event=0).
   Клиентские возвраты (после выкупа) в goods-return НЕ ОТРАЖАЮТСЯ.
2. **КМ невыкупов никогда не выбывали**: 64/497 заказов имеют закреплённый sgtin
   (orders/meta) — все 64 кода INTRODUCED в ЧЗ (cises_info живьём). Подавать нечего.
3. **op=2 (excise return) не пришёл ни разу за всю жизнь платформы** (0 событий
   kind=return/return_apply). Триггер PENDING_RETURN мёртв → кнопка «Собрать возврат»
   (LP_RETURN) недостижима. WB не шлёт возвратные чеки FBS в эксайз.
4. **Клиентские возвраты после выкупа WB обрабатывает сам**: чек продажи (retired) →
   возвратный чек (introduced) → товар в стоке WB → перевыставление → повторная продажа
   тем же КМ (доктрина RESALE подтверждена). Живое: 14 журнальных кодов с фискальными
   чеками снова introduced; 4/5 легаси-RESALE закрыты cis-sync 23.09 (юзер жал кнопку).
5. **expiredDt WB перестал отдавать** (0/750 непустых) → дедлайн-алерты и колонка
   «Забрать до» мертвы. Регламент WB: готовность → 7 дней на забор (3 бесплатно,
   дальше 10 ₽/день/ед), на 8-й — назад на склад WB. Фолбэк: readyToReturnDt + 7 дней.
6. **Сентябрьский чек-сплит продолжается**: продажи 15–22.09 почти без
   fiscal_doc_number (25/29 NULL) → WB не выводит чеками → коды introduced → вывод
   делаем МЫ (LK_RECEIPT «Иное»). Все 22 текущих «к выводу» — introduced, это ШТАТНО
   для этого потока (вывод из оборота законен только по коду в обороте).
7. Возвратные srid живут в другом пространстве (mp.<hash>.r) vs эксайз (eAW.<hash>.n.m):
   трассировка КМ секцию returns не матчит (там srid/order_doc-матчинг). Связка
   возможна только order_id → wb.orders.order_id → order_doc.

## 2. Ответ на вопрос «что делать с кодами»

- **Невыкуп** → в ЧЗ НИЧЕГО. Код в обороте. Забрать товар с ПВЗ (дедлайн!) → снова
  отгружать под новые заказы с теми же КМ (sgtin в meta закрепляем как раньше).
- **Клиентский возврат после выкупа** → в ЧЗ НИЧЕГО, пока WB перевыставляет сам
  (текущая реальность 100%). Код введён возвратным чеком WB, перепродаётся тем же КМ.
- **LP_RETURN** — резервный контур на случай «товар физически у продавца, код retired,
  возвратного чека не было» (не наблюдался ни разу). Оставить кнопку, не строить UX.
- **Перемаркировка (СУЗ REMARK + LK_REMARK)** — только при физическом повреждении КМ
  у вернувшегося продавцу товара; ручной путь через ЛК ЧЗ, автоматизации нет (бэклог).

## 3. Гэпы платформы (кратко)

1. UX раздела «Возвраты»: KPI «к возврату в ЧЗ» вечно 0; реальная задача «забрать
   N единиц» не показана; нет стока возвратов (что вернулось по номенклатурам).
2. Дедлайн-мониторинг мёртв (expiredDt пуст) — нужен фолбэк readyToReturnDt+7д.
3. Журнал: «выведено WB + WB вернул в оборот» показывается как WITHDRAWN — картинка
   врёт, нужен бейдж «WB вернул в оборот» при cis introduced у WITHDRAWN.
4. Трассировка: секция returns не работает (п.1.7) — матчить через order_id.
5. 110/750 возвратов — «сироты» (заказ вне реестра wb.orders) — косметика.

## 4. КОРРЕКЦИЯ 23.09 (вечер, вопрос юзера «WB сам вернёт в оборот? Точно?»)

Вывод п.1.4 («клиентские возвраты WB обрабатывает сам, продавцу ничего») — **ОШИБОЧЕН**,
опровергнут тремя живыми проверками:

1. **introducedDate не обновляется при возврате в оборот** — тестовый код E2E 04.09
   (эмиссия 09:28 → первый ввод 09:37 → наш LK_RECEIPT → LP_RETURN CHECKED_OK) до сих пор
   показывает introducedDate = 09:37 первого ввода. Поле непригодно как детектор.
2. **Все 26 introduced-кодов журнала НИКОГДА не выбывали**: introducedDate = даты эмиссий
   партий (2025-05-30…2026-04-29), т.е. ДО их продаж. Это «недовыведенные» продажи
   (чеки без КМ), а НЕ «вернувшиеся в оборот». DUNGR52: 2 продажи (16.09, 20.09),
   статус INTRODUCED → сентябрьские чеки код вообще не трогали.
3. **Возвраты покупателей существуют финансово, но НЕ оставляют ЧЗ-следа**: sales-отчёт
   за 30 дней = 108 R-строк (все «Склад WB РФ» — признак НЕ классифицирует контур,
   коррекция 14.09); эксайз op=2 = 0 за всю жизнь; goods-return связи с продажами = 0.
   Товар по словам юзера возвращается на фулфилмент продавца.

**ДОКТРИНА v3**: после излома 01.09 WB-чеки идут БЕЗ КМ → ЧЗ-статус кода не меняется
НИ при продаже, НИ при возврате покупателя. До 01.09 чеки с КМ выводили код; возврат
такого кода покупателем НЕ возвращает его в оборот (следа нет) → **товар на фулфилменте
с retired-кодом застревает: в ЧЗ «выбыл», продать нельзя, нужен LP_RETURN**. Это и есть
реальная работа «вернуть в оборот», и она платформой не видна.

Следствия для платформы:
- Детектор клиентских возвратов = sales R-строки (108/30дн, квота 1/2ч) + связка с КМ
  через finance `/api/v1/finance/v1/sales-reports/detailed` (поле kiz — ресерч 30.08).
- R ДО нашей подачи вывода → обязательство снять (код introduced, продажа отменена) —
  иначе выведем непроданное (ЛОЖНЫЙ вывод).
- R ПОСЛЕ вывода (retired/wb или us) → PENDING_RETURN → LP_RETURN (контур готов,
  return_batch умеет us/wb первичку) — кнопка «Собрать возврат» оживёт с реальными данными.

## 5. КОРРЕКЦИЯ-2 (23.09 поздний вечер): решающая проверка R-возвратов × коды

Проверка: 10 напечатанных R-строк sales сопоставлены с журналом по doc-префиксу srid
(правильный doc = первые ДВА сегмента 'eAW.<uuid>', не один — split_part('.',1) ловит
только 'eAW'). Результат: **4/10 — наши августовские продажи с fiscal_doc_number, и все
4 кода сейчас INTRODUCED + PENDING_WITHDRAW**. Вероятность попасть всем четырём в хвост
недовыведенных (16%) = 0,07% → августовские ВОЗВРАТЫ WB возвращал в оборот сам
(возвратный чек с КМ; introducedDate при этом не обновляется — см. §4.1).

### ИТОГОВАЯ ДОКТРИНА v4 (две эпохи кассовых чеков WB)

| | До ~01.09 (август) | После 01.09 (сентябрь) |
|---|---|---|
| Чек WB | с КМ | без КМ (чек-сплит) |
| Продажа → код | WB выводит сам (84%; хвост 16% — наш LK_RECEIPT) | НЕ выводится → выводит ТОЛЬКО наш LK_RECEIPT |
| Возврат → код | WB возвращает сам (доказано 4/4) | не меняется (и не выводился — товар годен к перепродаже тем же КМ) |
| Роль платформы | хвостовая (16% продаж) | ОСНОВНАЯ по выводу (100% продаж) |

Дыры (реальные):
1. сентябрьская продажа + R-возврат ДО нашей подачи → обязательство вывода ЛОЖНО (4 таких
   кода уже в очереди 22 «к выводу»!) — надо снимать, иначе выведем непроданное;
2. продажа + R-возврат ПОСЛЕ нашей подачи (или после августовского вывода, если такие
   найдутся) → код retired, товар на фулфилменте → нужен LP_RETURN;
3. детектор возвратов = sales R-строки: связка R.srid ↔ журнал по doc работает (4/10 —
   наши; полный перерасчёт 108 R — после квоты sales 1/2ч, фоново);
4. невыкупы (750) — вне ЧЗ, операционный забор; op=2 мёртв навсегда как триггер.

Платформа устойчива к смене эпох по построению: пре-флят cises/info + гварды корректно
работают в обе стороны (introduced → наш документ, retired → 'вывел WB').

## 6. КЛЮЧ ЮЗЕРА 23.09 (финал): доменная модель контуров

Слова юзера: «с сентября перешли на работу через фулфилмент по модели FBS (FPS), но
остатки на складах WB ещё есть и распродаются по FBO (FPO)». Это снимает последнее
противоречие: «Склад WB РФ» = FBO-контур → 108 R-возвратов и RESALE-перепродажи =
WB сам (участник оборота при FBO, ПП 1351): возвращает коды, перевыставляет товар.
Новая партия (Kizi, эмиссия 31.08) = FBS-фулфилмент: сентябрьские продажи без КМ в
чеках — норма нового канала; вывод только наш; FBS-возвраты (R со склада продавца)
пойдут волной с конца сентября — детектор строим до первой волны.
Дискриминатор контура R-строки: warehouseName («Склад WB РФ» = WB-зона, код не трогаем;
склад продавца = наш FBS, код — наш долг). Терминология юзера: FPS=FBS, FPO=FBO.
