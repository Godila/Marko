# Наборы (sets) в Нацкаталоге — дизайн фичи

Дата: 2026-09-22. Статус: дизайн представлен юзеру, реализации пока нет.
Пайплайн: /feature-dev (explorer→architect→TDD→reviewer), ниже — зафиксированный дизайн.

## 1. Задача и домен

Юзер (YCPB, лёгпром, WB FBS) продаёт наряду с единицами товара **наборы** — чаще всего
«шапка + шарф». Набор = самостоятельный товар со **своим GTIN**, маркируется **одним кодом
(КИН)** на упаковку. Это НЕ комплект (у комплекта свой ТНВЭД-критерий 6302/6103/6104/6203/6204,
производитель задаёт при производстве, не разбирается; шапка+шарф под комплект не подходит).

Ключевое требование юзера: набор собирается **из уже существующих опубликованных карточек**
(наши GTIN) — «тупая регистрация всех вложений заново не помогает».

## 2. Живой ресерч API (прод-проба 22.09 + доки docs.crpt.ru / markirovka.ru)

### 2.1 Проверено живьём на проде (read-only, токен из platform.kv mt_token)

`GET {mt_base_v3}/nk/attributes?tnved=6505009000&is_set=true` — работает, возвращает
**атрибутный состав карточки набора лёгпрома — всего 6 атрибутов** (против ~12 у обычной
карточки; нет вида товара/размера/цвета/состава-тканей/декларации 23557/производителя):

| attr_id | Название | Тип | Обяз. |
|---|---|---|---|
| 2478 | Полное наименование товара | text | m |
| 2504 | Товарный знак | text | m |
| 3959 | Группа ТНВЭД | text (preset) | m |
| 23768 | Товарная группа | text (preset) | m |
| 16271 | **Состав набора** (текст немаркируемых вложений) | text | r |
| 23821 | **Количество маркированных товаров в наборе** | number | r |

`GET /nk/product?gtin=<gtin>` — работает, в ответе есть `is_set`, `is_kit`, `set_gtins[]`,
`good_status` (в т.ч. `archived`), `good_mark_flag`, `identified_by` — канал чтения наборов
из ЧЗ для «Проверить в ЧЗ».

### 2.2 Создание набора — обычный фид

`POST /nk/feed`, entry дополнительно к обычным полям несёт:
`is_set: true`, `set_gtins: [{gtin, quantity}, ...]` («указывается только с is_set=1»),
`is_kit` — для комплектов (не наш случай). Предел: ≤1000 GTIN в наборе (иначе 413), фид
≤500 товаров / ≤25 МБ. Лёгпром-нюанс: `set_gtins[].gtin` для ТГ «лёгпром» **не обязателен**
— состав можно задать только количеством (23821); при пустых привязках в КИН допускаются
любые GTIN в количестве из карточки (правило SETS_AGGREGATION).

Ответ `{result: {feed_id}}` → `GET /nk/feed-status` → модерация (`GET /nk/feed-moderation`)
→ подписание `feed-product-document` (≤10) + УКЭП → `feed-product-sign-pkcs` — **весь
существующий конвейер МАРКО переиспользуется без изменений** (worker `nkmt_cycle` тоже).

### 2.3 GTIN набора

`GET /nk/generate-gtins?quantity=N` — тот же метод (в МАРКО уже есть), 13 цифр → zfill(14),
monthly-limit 11000. «Наборности» в методе нет — тип задаётся карточкой (`is_set`).

### 2.4 Дальний контур (фаза 2, НЕ входит в фичу)

- СУЗ: заказ на GTIN набора, `cisType: "SET"` (справочник типов упаковки: UNIT/SET/BUNDLE).
  СУЗ-контура в МАРКО нет вообще — отдельная будущая фича.
- Формирование КИН: документ ГИС МТ `SETS_AGGREGATION` (unitSerialNumber=КИН,
  sntins=КИ вложений; карточки компонентов должны быть published; после агрегации набор
  автоматически вводится в оборот; продажа/чек = авторасформирование и вывод КИН).
- WB: штрихкод карточки WB = GTIN набора. **Гейт-неизвестность**: отдаст ли WB КиЗ на
  заказ набор-листинга корректно (SET). Первый живой набор-заказ покажет; если нет —
  фаза 2 (СУЗ) становится обязательной.

## 3. Решения (допущения вместо уточняющих диалогов — юзер пропускает)

1. **Режим по умолчанию — привязанный набор** (set_gtins с конкретными GTIN наших карточек):
   честное соответствие карточка↔физический состав↔WB-листинг (у каждого сочетания цветов
   свой GTIN = свой штрихкод WB). Режим «без привязки» (только количество 23821) —
   опциональный чекбокс для опытных (одна карточка на все двойки), с hint о последствиях.
2. **UI живёт в «Каталоге НК»** как таб-чип «Наборы» (паттерн табов как в Справочниках):
   новый топ-раздел не заводим, NAV не трогаем.
3. **Наборы создаются только конструктором в UI** (не xlsx): юзер выбирает компоненты
   из published-карточек. Импорт-файлы для наборов — YAGNI.
4. **Правка до подачи** — тот же конструктор в режиме edit; **после подачи — read-only**
   (состав опубликованного набора менять нельзя — риск несоответствия КИН карточке;
   «Собрать аналог» покрывает потребность в вариациях).
5. **Статусы не расшираем** (DESIGN.md §8): CARD_STATUS/BATCH_STATUS как есть. `archived`
   из /nk/product показывается текстом в drawer без нового бейджа.
6. Декларация/производитель набору не нужны — их нет в атрибутном составе набора (проверено
   живьём §2.1); РД остаются на компонентах.
7. Правила/дефолты НКМТ (RULE_FIELDS, resolve) не трогаем — они для xlsx-импорта обычных
   карточек; конструктор берёт поля явно.

## 4. Подходы (рассмотренные)

- **A. Отдельная сущность + конструктор (ВЫБРАНО)**: `cards.is_set` + таблица
  `nkmt.set_items`, мастер сборки, мини-роуты /v1/nkmt/sets поверх существующего конвейера
  батчей. Чистый UX «выбрал карточки → получил набор», все валидации локальны.
- **B. Через xlsx-импорт (отвергнут)**: колонка «Состав набора: GTIN×2, GTIN×1». Дёшево,
   но UX мимо задачи (файл ради одного набора), парсер и preview усложняются.
- **C. Только реестр чужих наборов без создания (отвергнут)**: дёшево, задачу не решает;
   чтение из ЧЗ включено в A как «Проверить в ЧЗ».

## 5. Архитектура (фаза 1)

### 5.1 Модель (миграция 0019)

```
ALTER TABLE nkmt.cards ADD COLUMN is_set BOOLEAN NOT NULL DEFAULT FALSE;
CREATE TABLE nkmt.set_items (
  id SERIAL PRIMARY KEY,
  card_id INTEGER NOT NULL REFERENCES nkmt.cards(id) ON DELETE CASCADE,
  gtin VARCHAR(32) NOT NULL,
  quantity INTEGER NOT NULL CHECK (quantity > 0),
  UNIQUE (card_id, gtin)
);
```
Набор = Card(is_set=true) в собственном Batch (1 набор = 1 батч, source_filename
«конструктор наборов»). Обычные списки карточек фильтруют `is_set=false`, список наборов —
`is_set=true`. FK на компонент по gtin НЕ делаем (компонент может быть внешним GTIN).

### 5.2 Сервис

- `service._feed_entry(card)`: при `is_set` строит entry c `is_set:true`,
  `set_gtins:[{gtin, quantity}]` (привязанный режим) и good_attrs
  `[2478 name, 2504 brand, 23821 итого-предметов, 16271 состав-текст (если дан)]`;
  3959/23768 не шлём (preset, НК выводит из tnved — сверить на первой живой подаче).
- Кэш атрибутов: `nk_attrs_set:{tnved}` (dicts.attrs_model обобщить параметром is_set;
  NkClient.attributes получает `is_set: bool | None = None` → param `is_set=true`).
- `NkClient.product(token, gtin)` — GET /nk/product (для «Проверить в ЧЗ» набора:
  статус/is_set/set_gtins из ЧЗ; живьём проверено 22.09).
- Генерация GTIN набора — существующая логика feed_batch (пустой gtin → generate-gtins).

### 5.3 API (scope `nkmt:import`, аудит `nkmt.set.*`)

| Метод | Роут | Назначение |
|---|---|---|
| GET | `/v1/nkmt/sets` | список наборов + компоненты (+имена наших карточек по gtin) |
| GET | `/v1/nkmt/sets/cards?q=` | пикер: published-карточки с gtin (поиск article/gtin/name) |
| POST | `/v1/nkmt/sets/preview` | dry-run валидации + предзаполнение (ошибки/предупреждения) |
| POST | `/v1/nkmt/sets` | создать (Card+set_items+Batch new) |
| PUT | `/v1/nkmt/sets/{id}` | правка до подачи |
| DELETE | `/v1/nkmt/sets/{id}` | удалить черновик (только до подачи) |
| POST | `/v1/nkmt/sets/{id}/feed` | подать фид (обёртка над feed_batch) |
| POST | `/v1/nkmt/sets/{id}/check` | «Проверить в ЧЗ» через /nk/product |

Подача/обновление/подписание дальше — существующие `/batches/{id}/feed|refresh|sign`.

### 5.4 Валидации (preview)

- Состав: ≥1 компонент; дубли gtin блок (uq); сумма количеств ≤1000 (413 ЧЗ).
- Компонент из нашего каталога: `status='published'` + непустой gtin — иначе блок с
  внятным текстом. GTIN не из нашего каталога: допускаем, предупреждение «внешний GTIN —
  ЧЗ проверит на фиде».
- Unbound-режим: 23821 указывается вручную (≥1); привязанный: 23821 = Σ quantity (readonly).
- ТНВЭД набора: свободный выбор из nk-словаря; подсказка = ТНВЭД первого компонента;
  предупреждение при разных ТНВЭД компонентов (GS1 — одна категория).
- Дедуп-предупреждение: существует набор с тем же мультимножеством (gtin, qty) не в
  терминальном статусе → warn «похожий набор уже есть».
- Наименование: автоподсказка «Набор: {имя1} + {имя2}», редактируется; article авто
  `SET-####` (уникальность как у обычных карточек).
- Удаление/правка — только пока карточка не подана (status ок/new до feed).

## 6. UX/UI (DESIGN.md §7, без новых статусов/цветов)

- «Каталог НК» → таб-чипы «Карточки | Наборы». В табе «Наборы»: кнопка «Собрать набор…»,
  пусто-состояние «Соберите первый набор из опубликованных карточек», грид.
- **Грид наборов** — table.t.fit + colgroup (все ширины заданы, §7/§13): Артикул | GTIN
  набора | Название | Состав (чипы-бейджи «{имя} ×N», EllCell-раскрытие при 3+,
  бейджи переносятся внутри колонки) | Статус (CARD_STATUS) — строка кликабельна →
  drawer (паттерн DeclarationCard: действия в карточке, не в строке).
- **Drawer набора**: состав списком (наши компоненты — ссылки на карточки, внешние —
  gtin), атрибуты, статус конвейера, кнопки по состоянию: до подачи — «Подать фид /
  Изменить / Удалить»; после — «Обновить / Подписать / Проверить в ЧЗ» + hint
  «GTIN набора используйте как штрихкод карточки WB» + «Собрать аналог» (мастер,
  предзаполненный текущим набором).
- **Мастер «Собрать набор»** — модалка .modal.wide, 3 шага с футером (Назад/Далее/Создать):
  1. **Состав**: поиск по published-карточкам (article/GTIN/название), клик — добавить,
     выбранные — чипы с qty-степпером ±, счётчик «Итого предметов: N».
  2. **Карточка набора**: наименование (авто), бренд, ТНВЭД (селект + warn), чекбокс
     «Не привязывать GTIN компонентов (собирать из любых остатков)» — при включении
     состав скрывается, 23821 вручную; «Состав набора» (текст немаркируемых, опц.).
  3. **Проверка**: POST /sets/preview — ошибки (red) / предупреждения (amber) / сводка;
     свёрнутый тех-предпросмотр entry фида; «Создать и подать» (moderation:1) или
     «Создать черновик».
- Правка = тот же мастер с предзаполнением (паттерн edit-режима справочников).
- Адаптив 900px: модалка и грид по стандартным правилам (wide-модалка, twrap-скролл).

## 7. Тесты (TDD, ~12)

preview-валидации (пустой состав / не-published / внешний gtin-warn / дубли / сумма>1000 /
дедуп-warn / unbound); POST создаёт Card(is_set)+set_items+Batch; _feed_entry строит
is_set+set_gtins+23821+16271; кэш атрибутов отдельный ключ is_set; PUT правка; DELETE
черновика + запрет после подачи; /check на моке NkClient.product; RO-скоп 403;
sets/cards-поиск фильтрует published.

## 8. Фазы и гейты

- **Фаза 0 (при старте реализации)**: живая сверка полного good_attrs реальной карточки
  (23768/3959 значения, categories в entry набора) — читаем /nk/product своих карточек;
  первая подача боевого набора — только по явному разрешению юзера (мутация ЧЗ).
- **Фаза 1 (эта фича)**: §5+§6, /feature-dev конвейер, TDD, ревью, QA-моки Playwright,
  DESIGN.md §7 + пункт «Наборы».
- **Фаза 2 (отдельная фича, после гейтов)**: СУЗ-контур (cisType SET) + SETS_AGGREGATION
  (сборка КИН) + авторасформирование/вывод КИН в журнале. Гейт: как WB отдаёт КиЗ на
  набор-листинг (первый живой заказ); СУЗ-ресерч в crpt-specs/trueapi-auth-nkmt-suz-discovery.md.

## 9. Риски

- Состав после публикации неизменяем (вероятно) — read-only после подачи, «аналог» вместо
  правки. НЕ ПРОВЕРЕНО до первой живой подачи.
- WB может не уметь заказывать КиЗ типа SET на FBS → фаза 2 обязательна. Проверить первым
  живым набор-листингом.
- Пресет 23768/3959: если фид набора их потребует явно — добавить в _feed_entry по
  результатам фазы 0 (первая подача покажет ошибки фида в refresh).
