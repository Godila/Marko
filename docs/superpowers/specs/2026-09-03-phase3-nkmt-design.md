# Фаза 3: модуль НКМТ — массовое создание карточек (спека)

Дата: 2026-09-03. Ревизия дизайна фазы 3 из
`2026-09-02-mp-gis-mt-platform-design.md` (блок 2, НКМТ-поток) на основе живого ресерча
(`crpt-specs/nk-live-research-2026-09-03.md`) и брейншторма с владельцем.

## 1. Цель и рамки

Массовое создание карточек товаров в Национальном каталоге из одного упрощённого xlsx
(смешанные товарные группы в одном файле), с автоподстановкой констант, вплоть до
**published + готовность к эмиссии КМ**, с выходом GTIN-фактуры. Потребитель —
REST API (равные клиенты: UI и AI-агент). Вход почти всегда xlsx; JSON — позже, второй
веткой парсера (out of scope этой фазы).

Подтверждённые решения владельца:
- GTIN: 99% — генерация через НК `/nk/generate-gtins` (прод: лимит 11000/мес); колонка
  `gtin` опциональна для редких существующих кодов.
- MCP-контейнер — ОТЛОЖЕН (следующий этап, тонкая обёртка над этим же REST).
- Автоподписание воркером карточек после модерации — да.
- Реестр разрешительных документов (РД) — локальная персистенция с CRUD через REST.
- «Второй этап» (отдельный импорт РД в ЛК) — УПРАЗДНЯЕТСЯ: атрибут 23557 «Декларация о
  соответствии» (`номер:::дата`, 2-й слой — заполняется при создании черновника) кладём
  прямо в первый feed. **Допущение** (проверить первым тест-батчем в песочнице): feed
  принимает РД при создании. Если НЗ отклонит — fallback: обновление 2-го слоя до
  модерации вторым feed по good_id.

Вне scope: СУЗ/эмиссия КМ, субаккаунты, зеркалирование чужих карточек, фото, редактирование
3-го слоя, полная синхронизация каталога (etagslist), JSON-импорт, MCP.

## 2. Ключевые технические факты (из живого ресерча)

1. Методы НК — на True API-стенде: `{mt_base_v3}/nk/*` (categories, attributes, brands,
   product, short-product, feed, feed-status, feed-moderation, feed-product-document,
   feed-product-sign-pkcs, generate-gtins, mark-check, etagslist, image, linked-*).
   Тот же Bearer (`manager.get_token`), тот же signer (`doc_sign` — откреплённая CAdES,
   уже работает). Второй базы/секрета нет.
2. categories/attributes требуют **10-значный ТН ВЭД**; без параметров categories отдаёт
   всё дерево (1885 узлов); `tnved=X` → список категорий этого кода (0, 1 или несколько —
   при нескольких нужна колонка `категория`).
3. Атрибутная модель: записи с `attr_field_type`, `attr_preset[]` (справочник допустимых
   значений), `attr_preset_only`, `attr_value_type[]` (квалификаторы: тип артикула,
   размерные системы), `attr_multiplicity`, `first_layer/second_layer`,
   `dependent_attributes`. Образец 6109100000: 11 обязательных + 37 рекомендуемых.
   Артефакты-фикстуры: `crpt-specs/nk-attrs-6109100000-{m,r}.json`,
   `nk-categories-full.json`.
4. Бренды: `/nk/brands?name=` (частичное совпадение, limit≤10000). YCPB=2102811;
   в реальных файлах бывает и ADEL → бренд = дефолт + колонка-переопределение.
5. Песочница: `/nk/*` на `markirovka.sandbox.crptech.ru/api/v3/true-api` работает,
   данные идентичны продовым; `generate-gtins` в ТК заблокирован настройкой организации
   («только ГС1») → в песочнице флоу тестируем с явно указанными gtin.
6. Официальный шаблон НК (Hats import.xlsx, категория 30728): 18 колонок, во 2-й строке —
   attr_id (совпадают с нашей моделью); GTIN/категория/статус — служебные; справочники —
   лист с preset'ами. Наш шаблон — упрощение этого формата; подача через API `/nk/feed`,
   официальный xlsx не генерируем.

## 3. Архитектура (вариант 1 — «лёгкий реестр», одобрен)

Доменный пакет `mpmt.nkmt` по образцу существующих модулей:
`client.py` (HTTP /nk/*), `validate.py` (парсинг+валидация), `service.py` (конвейер
батча), `models.py` (batches/cards/declarations/brand_cache), `routes_nkmt.py` (REST),
воркер-цикл в `worker.py`. Клиент — ретраи 429/5xx 1/4/16с (общий паттерн), лимиты НК
(series/5мин, счётчики в заголовках, ETag для брендов/категорий — опционально).

### Поток данных

```
xlsx → POST /v1/nkmt/import
  → парсинг (12–13 колонок, смешанные ТН ВЭД)
  → валидация построчно против ЖИВОЙ модели своего ТН ВЭД (кэш 24ч):
      формат (10 цифр, Unicode-фильтр), обязательные, preset'ы (вид товара/цвет/техрегламент),
      квалификаторы (размерная система), бренд (кэш/НК), РД (наш реестр), категория (авто по
      ТН ВЭД; несколько категорий → колонка или ошибка со списком), дедуп (артикул UNIQUE,
      gtin занят)
  → дефолты платформы подставляются в пустые ячейки (kv nk_defaults, редактируемый)
  → nkmt.batch(new|partial) + nkmt.cards(ok|error+текст)
  → POST /v1/nkmt/batches/{id}/feed:
      generate-gtins (строки без gtin, пачки) → POST /nk/feed (≤500, moderation:1)
      → batch.feed_id
  → воркер (раз в ~10 мин) + POST refresh: feed-status → карточки moderation/notsigned/errors
  → авто-подписание notsigned: feed-product-document (батчи ≤10) → doc_sign (наш signer) →
      feed-product-sign-pkcs → published → TG-уведомление на финальных статусах
  → GET /v1/nkmt/batches/{id}/report → выгрузной артефакт для 1С: XLSX с двумя
     колонками «GTIN | Наименование» (published-карточки батча; подробности —
     статус/атрибуты/good_id — в UI и API карточек, в файл не пишем)
```

Ошибки модерации: правка xlsx → повторный импорт: существующий `article` обновляет
карточку и перевалидируется (feed обновляет по gtin/good_id); `errors`-строки видны с
текстом причины. Feed Processing>24ч → НК переведёт в Rejected — refresh покажет,
повторная подача руками.

### Шаблон xlsx (наш, единый для всех товарных групп)

Колонки пользователя:
`ТН ВЭД* (10 цифр) | наименование* | вид товара* | цвет* | состав* | размер* |
модель/артикул | бренд | целевой пол | размерная система | декларация | категория (опц.,
только если по ТН ВЭД несколько категорий)`

Дефолты платформы (kv `nk_defaults`, редактируются через REST/UI, применяются к пустым
ячейкам, зафиксированы в карточке — прозрачно):
`бренд (YCPB|ADEL|…), техрегламент (ТР ТС 017/2011…), целевой пол, размерная система
(МЕЖДУНАРОДНЫЙ), страна, производитель, декларация (текущая действующая из реестра РД)`.

### Модель данных (миграция 0006)

- `nkmt.batches`: id, status (new|partial|feeding|moderation|signing|published|error),
  source_filename, feed_id, stats json, created_at.
- `nkmt.cards`: id, batch_id FK, **article UNIQUE**, gtin UNIQUE nullable, good_id,
  tnved, name, attributes json (attr_id→значения, нормализовано), cat_id,
  status (ok|fed|moderation|notsigned|signing|published|error|errors|error_sign),
  error_text, created_at, updated_at.
- `nkmt.declarations`: id, doc_number, doc_date, doc_type (declaration|certificate),
  title; UNIQUE(doc_number, doc_date).
- `nkmt.brand_cache`: name UNIQUE, brand_id, updated_at.
- Атрибутные модели: `platform.kv` `nk_attrs:{tnved}` = {fetched_at, model}; TTL 24ч.

### REST ( scopes: запись nkmt:import, чтение read)

| Метод | Назначение |
|---|---|
| POST /v1/nkmt/import (multipart xlsx) | парсинг+валидация → батч + статусы строк |
| GET /v1/nkmt/batches[?status=] | список батчей |
| GET /v1/nkmt/batches/{id}[?card_status=] | батч + карточки |
| POST /v1/nkmt/batches/{id}/feed | generate-gtins + feed |
| POST /v1/nkmt/batches/{id}/sign | подписание вручную (дубль воркера) |
| POST /v1/nkmt/batches/{id}/refresh | пересинка статусов |
| GET /v1/nkmt/batches/{id}/report | артефакт для 1С: XLSX «GTIN \| Наименование» (published); `?format=csv` опция; машиночитаемый формат — в будущем |
| GET/POST/DELETE /v1/nkmt/declarations[/{id}] | реестр РД |
| GET /v1/nkmt/dicts/attributes?tnved= | атрибутная модель (агент/UI) |
| GET /v1/nkmt/defaults, PUT | дефолты платформы |

### UI (вкладка «Каталог») — в скоупе фазы 3 в функциональном виде

Список батчей (статус, ok/error, дата) → карточки с фильтром статуса; кнопки Импорт /
Обновить / Подать / Подписать / Отчёт; блок «Декларации» (CRUD); блок «Дефолты».
Статус GTIN-лимита (usage из generate-gtins) — в стате батча. Полировка UX/UI —
отдельными сессиями после рабочего каркаса (решение владельца 2026-09-03).

## 4. Тесты и контуры

- Юнит: валидатор (фикстуры: валидный смешанный файл + все виды ошибок), нормализация
  атрибутов/дефолтов, стейт-машина батча, кэши (TTL, инвалидация), реестр РД.
- Контракты клиента /nk/* на моках; **живые артефакты ресерча как фикстуры справочников**
  (nk-attrs-*.json). Валидатор гоняем против реальных preset'ов.
- Воркер: фейк-клиент прогоняет батч new→published без сети.
- E2E вручную в песочнице ТК (скрипт по образцу ресерча): импорт 2–3 позиций с указанными
  gtin + декларацией → feed → модерация → подписание → published; проверка допущения
  «РД в первом feed». Генерация GTIN в ТК недоступна — на проде.
- Деплой на прод; **первый боевой батч 3–5 позиций под контролем**, затем массово.
- Гейт выноса репо на shared remote: реальное имя продавца/бренды в фикстурах — решить до
  публикации (унаследовано из фазы 1).
