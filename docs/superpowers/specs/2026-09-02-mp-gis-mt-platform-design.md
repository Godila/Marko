# MP-GIS_MT Platform — Design (согласовано)

Статус: **согласовано с владельцем 2026-09-01/02** (блоки 1–2 — 01–02.09, блок 3 — 02.09). Следующий шаг — writing-plans (план реализации фазы 0/1).
Git-репозитория на момент согласования нет; заводится в фазе 0, эта спека — первый коммит.

## Контекст и вводные

- Пользователи: один продавец (ИП Байкулов Д. А., WB, лёгпром — одежда второго слоя). Не SaaS, без мультитенантности.
- Задачи платформы, по убыванию приоритета:
  1. Контур вывода КИЗ из оборота для проданных на WB FBS (LK_RECEIPT, DISTANCE) и возврата в оборот выкупленных-и-возвращённых (LP_RETURN, REMOTE_SALE_RETURN).
  2. Каталогизация в НКМТ: массовое создание карточек (xlsx-импорт + поштучно), на выходе GTIN-фактура.
  3. Управление: UI для человека + REST/MCP для AI-агента с равными возможностями.
- Вне scope: эмиссия КМ — коды заказываются вручную в ЛК СУЗ (решение владельца 02.09), платформа не автоматизирует СУЗ; фулфилмент получает готовые этикетки с DataMatrix.
- Подпись УКЭП: закрытый сервер с КриптоПРО (РФ), входящие запрещены — только исходящие. Скрипт подписи отработан.
- Стек: Python 3.12 / FastAPI + React UI + PostgreSQL 16, docker-compose.
- Хостинг: **Beget VPS (РФ), 2 vCPU / 4 GB**, домен gis.adel-factory.ru, доступ — secrets/VMsecrets.txt (в фазе 0 перевести на SSH-ключ, отключить password-auth). Вся критичная инфраструктура (API ЧЗ, КриптоПРО-машина) — в РФ: меньше задержек и нет трансграничных рисков; API WB доступен из РФ; ПДн покупателей в системе нет. Вертикальный скейл без переписывания.
- Будущее расширение (вне фаз 0–3): контур Ozon FBS (продажи/возвраты → те же LK_RECEIPT/LP_RETURN). Журнал и emitter мульти-источниковые по построению (см. блок 1); перед реализацией — отдельный ресерч Ozon Seller API.
- Ресерч завершён: WB — `wb-specs/research-log.md` (+ фикстуры прод/песочница, сценарий `scripts/sandbox_scenario.py`); ЧЗ (авторизация/НКМТ/СУЗ/вывод из оборота) — `crpt-specs/trueapi-auth-nkmt-suz-discovery.md`.

## Блок 1. Архитектура, модули, модель данных

Модульный монолит + отдельный signer. API-first: UI, агент (MCP), signer — через один REST `/v1`.

```
Beget VM (РФ): [ caddy | api | worker | ui | postgres ]  ←— исходящий поллинг (lease-очередь) —→  Signer (закрытая машина, РФ, КриптоПРО)
```

Доменные модули (Python-пакеты): `connector_wb`, `journal` (стейт-машина по КМ), `emitter` (LK_RECEIPT/LP_RETURN), `connector_mt` (True API), `nkmt`, `sign_gateway`, `notifier` (TG-алерты), `platform` (принципалы/scopes/аудит/настройки).

**Граница для мульти-маркетплейсов (Ozon на будущем)**: `journal` и `emitter` не знают про конкретный маркетплейс — коннектор нормализует источники в события `SaleEvent` / `ReturnEvent` (поля: `source` = 'wb' | 'ozon', `source_event_id`, `km`, `srid`, модель продажи fbs/fbw, суммы) и сам отвечает за фильтрацию чужих моделей (FBW у WB — в «пропущено» уже на уровне коннектора). При появлении Ozon добавится пакет `connector_ozon`, реализующий тот же тонкий контракт событий; никакой generic-абстракции с одним реализатором сейчас не строим.

Модель данных (Postgres, схема на домен):
- `journal.items` — стейт-машина по ключу `km`; `journal.events` — события источников, ключ идемпотентности (`source`, `source_event_id`), payload JSONB.
- `mt.docs` — документы ЧЗ (draft → signing → submitted → CHECKED_OK / error).
- `sign.tasks` — очередь подписи: lease_owner/lease_until, attempt, result.
- `nkmt.batches` / `nkmt.cards`; `platform.audit_log`.

Правило фильтрации: excise-строки не-FBS (FBW) не меняют стейт и не попадают в батчи — отдельный список «пропущено».

## Блок 2. Контур подписи, API/MCP, НКМТ

Signer-протокол (машина «только наружу»):
- `POST /v1/sign/lease` — long-poll до 30 c, одна задача, lease TTL 120 c; по истечении задача возвращается в pending.
- Типы задач: `auth_sign` (data из GET /auth/key, присоединённая подпись — для simpleSignIn), `doc_sign` (откреплённая УКЭП: product_document ЧЗ и XML карточек НК — один тип задачи).
- `POST /v1/sign/results` — подпись или ошибка; heartbeat; алерт при молчании > 2 ч.
- Аутентификация signer — отдельный долгоживущий токен; аудит каждой подписи; УКЭП не покидает машину.
- Токен ЧЗ: единый токен UUID (`unitedToken: true` в simpleSignIn — новая логика с 01.09.2026), TTL 10 ч, кэшируется до exp, обновление за 10 мин. Один signer-флоу на все обновления (СУЗ-токенов нет — модуль СУЗ исключён).

API/MCP:
- Принцип: у агента нет прямых токенов WB/ЧЗ/БД — только токен платформы со scopes.
- Принципалы: пользователь (UI, сессия) и машина (статические токены). Scopes: `read`, `journal:manage`, `docs:submit`, `nkmt:import`, `signer`, `admin`.
- MCP-контейнер — тонкая обёртка над REST. Инструменты: `journal_status`, `withdraw_pending_list`, `batch_preview/create`, `nkmt_import_xlsx`, `nkmt_gtin_report`, `doc_status`, `anomalies_list`.
- «Тормоз» (первый месяц прод-эксплуатации): `docs:submit` для батчей > N позиций требует подтверждения из UI.

НКМТ-модуль: авторизация только Bearer-токен True API (статический apikey НК не использовать — по факту практики отключён, доки отстают); xlsx (шаблон атрибутного состава лёгпрома) → валидация (mark-check, /v3/attributes, Unicode-фильтр) → feed (≤500/фид) → feed-status → feed-product-document + doc_sign (батчи ≤10) → published → GTIN-фактура (xlsx/csv). Дедуп по артикулу/GTIN.

## Блок 3. Инфраструктура, ошибки, тесты, фазы

### 3.1. Инфраструктура и деплой

Контейнеры (docker-compose): `caddy` (TLS Let's Encrypt, домен gis.adel-factory.ru), `api` (FastAPI), `worker` (тот же образ, режим воркера: поллинг WB, задачи очереди, батчи), `ui` (статика React за Caddy), `postgres` (16) + sidecar `backup` (postgres:16-alpine, shell-скрипт ~10 строк: nightly pg_dump → gzip → /backups, ротация 14 дней; фаза 1 — локально, фаза 2 — выгрузка наружу в S3-совместимое хранилище, провайдер выбрать при переходе — из РФ доступны и РФ, и ЕС-опции).

- Caddy вместо nginx: конфиг в три строки, сертификаты сам обновляет. Нужен: api доступен из интернета для UI и для signer-машины (long-poll).
- Деплой: `git pull && docker compose build && docker compose up -d`; downtime в секунды терпим. Без watchtower/CD.
- Секреты: `.env` + `secrets/` (монтирование в compose), без vault. Образы — фиксированные теги, обновление вручную.
- Observability-стек (Grafana/Prometheus/Sentry) — отложено на следующие этапы, не входит в фазы 0–3.

### 3.2. Ошибки, ретраи, алерты, тесты

Единый HTTP-слой всех коннекторов (WB/ЧЗ/НК):
- Ретраи только на 429 и 5xx: экспонента 1с → 4с → 16с, максимум 3 попытки; `Retry-After` уважается. 4xx — без ретрая.
- 401 — сброс кэша токена и один повтор.
- WB-лимиты: поллинг excise строго по расписанию (2×/день ровно в лимит базового токена 2/24ч), расход лимитов пишется в журнал.
- Идемпотентность: `source_event_id`, `(srid, km)` — повторные поллинги ничего не дублируют.

Очередь: задачи в Postgres (FOR UPDATE SKIP LOCKED); после 3 неудач — статус `failed`; «ручная очередь» = страница UI «Аномалии» (пере-запустить / пропустить / payload), не отдельный механизм.

TG-алерты (модуль `notifier`, bot token + chat id в настройках): signer молчит > 2 ч; документ ЧЗ не CHECKED_OK за 12 ч или ошибка; поллинг WB падает подряд / лимит исчерпан; бэкап не появился за 26 ч.

Логи: JSON в stdout, docker json-file с ротацией (10 МБ × 3). Health: `/healthz` у api и worker (Postgres + время последнего успешного поллинга). Внешний пинг домена (UptimeRobot) — опционально, вручную, вне кодовой базы.

Тесты:
| Уровень | Что | Чем |
|---|---|---|
| Unit | стейт-машина journal, emitter (LK_RECEIPT/LP_RETURN, фильтр FBS, копейки) | pytest, чистые функции |
| Контрактные | парсеры excise/orders/meta/НК на реальных фикстурах | pytest + `wb-specs/fixtures/` |
| E2E | живая песочница WB | `scripts/sandbox_scenario.py` — ручной запуск |
| Интеграционные ЧЗ | auth → короткий cis → LP_RETURN на тест-контуре | ручной smoke (gate фазы 2) |

CI на старте нет: локальный pytest перед деплоем.

### 3.3. Фазы (каждая — работающий деплой и видимая ценность)

**Фаза 0 — каркас (дни).** Git-репо (спека — первый коммит); compose со всеми контейнерами; Postgres + Alembic-миграции; `platform` (принципалы, scopes, аудит); `/healthz`; каркас notifier; SSH-ключ; деплой на gis.adel-factory.ru; UI-заглушка.

**Фаза 1 — WB-контур (ценность без подписи).** `connector_wb`: excise-поллинг 2×/день + orders/meta (полный КМ, фильтр FBS); `journal`; UI: реестры + черновики батчей LK_RECEIPT/LP_RETURN с выгрузкой (ручная подача в ЛК ЧЗ до появления signer); TG-алерты. Вход: базовый прод-токен WB. Выход: полный реестр продаж/возвратов, готовые документы.

**Фаза 2 — подпись, замыкание автомата.** `sign_gateway` + signer-агент (КриптоПРО); `connector_mt`: auth (UUID-токен), LK_RECEIPT/LP_RETURN, статусы до CHECKED_OK; «тормоз» подтверждения батчей; внешний бэкап. Gate перед стартом: УКЭП-инфраструктура + ручной smoke тест-контура ЧЗ (короткий cis 31 символ в LK_RECEIPT; REMOTE_SALE_RETURN).

**Фаза 3 — НКМТ + агент.** `nkmt`: xlsx → валидация → feed → статусы → подписание (doc_sign) → GTIN-фактура; MCP-контейнер. Gate: атрибутный ресерч лёгпрома (живые вызовы categories/attributes тест-контура, отдельная короткая сессия).

## Открытые вопросы (не блокируют writing-plans)

1. Персональный прод-токен WB (Аналитика/Статистика/Маркетплейс, только чтение) — нужен, когда поллинг чаще 2×/день или лимиты базового начнут срабатывать на 4XX-штрафы.
2. Smoke тест-контура ЧЗ (короткий cis, REMOTE_SALE_RETURN) — при готовности УКЭП; gate фазы 2.
3. Атрибутный состав карточки лёгпрома (attr_id, cat_id, ID бренда) — живые вызовы; gate фазы 3.
4. Префикс путей НК на стендах (`/v3/*` vs `/nk/*`) — проверить при первом живом вызове (в фазе 3).
5. Дата/статус отключения apikey НК уточняется у ТП ЦРПТ (на дизайн не влияет — Bearer-only).
